0 P-GPT vs API · CLI 환경

같은 Claude 모델이지만 사내 P-GPT 챗봇과 Claude Code CLI는 할 수 있는 일이 다릅니다. 이 매뉴얼은 CLI 환경 셋업을 다룹니다.

0-1 기본 기능 비교

기능 P-GPT 챗봇 (웹 UI) Claude Code CLI
출력 형태 마크다운 텍스트만 파일 직접 생성·수정
파일 저장 ❌ 없음 — 복사해서 직접 붙여넣기 ✅ HTML, Python, JS, CSV, JSON 등 직접 저장
명령 실행 ❌ 불가 ✅ PowerShell·Python 스크립트 실행 (Playwright 등으로 브라우저 자동화·스크린샷도 가능)
Office 파일 ❌ 불가 ✅ .xlsx · .docx · .pptx 생성 (라이브러리 필요)
컨텍스트 지속 ❌ 세션 끊기면 리셋 ✅ MEMORY.md로 대화 간 유지
프로젝트 규칙 ❌ 매번 설명 필요 ✅ CLAUDE.md에 한 번 써두면 자동 적용
병렬 처리 ❌ 불가 ✅ 서브에이전트 병렬 실행

0-2 MCP로 더 확장 가능

MCP(Model Context Protocol)는 Claude Code에 기능을 플러그인처럼 붙이는 확장 시스템입니다. 기본적인 MCP 예시:

MCP 역할
Tavily 웹 검색, URL 콘텐츠 추출 (키를 넣으면 크롤링·리서치까지)

→ Tavily가 여기 있는 이유: P-GPT 게이트웨이를 거치면 Claude Code 내장 WebFetch(URL 직접 열기)가 막힙니다. 설치기가 Tavily MCP를 붙여 두므로 키 없이도 이 제약을 우회해 웹 검색·페이지 콘텐츠 추출을 대신합니다. 무료 API 키(app.tavily.com)를 넣으면 사이트 지도·크롤링·리서치까지 씁니다.

→ MCP는 추가·제거가 자유롭고, 커뮤니티에서 만든 서드파티 MCP도 붙일 수 있습니다. DB 직접 조회, Slack 연동, GitHub 자동화 등 거의 모든 외부 서비스로 확장 가능합니다.

1 신규 PC에서 재현하는 순서

1-0 사전 조건

셋업 시작 전에 준비해야 할 두 가지:

  1. P-GPT API KEY 발급 — IT팀에 요청하세요. 없으면 이 문서 대부분이 안 굴러갑니다.
  2. GitHub 계정 가입 — github.com 접속, 개인 Gmail 계정으로 가입하는 것을 권장합니다. (사내 이메일로 가입하면 퇴사·조직 변경 시 계정 접근이 끊어집니다.) 커밋 이메일이 GitHub 가입 이메일과 같아야 프로필·아바타가 연결됩니다.

1-1 필수 프로그램 설치

1~4번은 순서 상관없이 설치해도 됩니다. 단, 5·6번(Codex CLI, Claude Code)은 3번 Node.js가 먼저 설치되어 있어야 npm 명령어가 동작합니다.

1 VS Code — code.visualstudio.com

→ 뭐하는 프로그램: 코드(글자로 된 명령서)를 쓰는 글자 편집기. 메모장의 강력한 버전이라고 생각하면 됩니다. 파이썬·자바스크립트 등 어떤 언어든 색깔·자동 완성으로 도와줍니다.
→ 코드를 쓸 창이 있어야 시작할 수 있음.

2 Git for Windows — git-scm.com

→ 뭐하는 프로그램: 코드의 "저장 이력"을 관리하는 도구. 언제 뭘 바꿨는지 다 기록해서 되돌리기·팀 공유가 가능해집니다. (자세한 건 [1-4] 아래 개념 설명.)
→ GitHub에 코드를 올리려면 필수. 함께 설치되는 Git Bash(터미널 창)와 GCM(GitHub 자동 로그인 도우미)이 이 문서 뒤쪽에서 계속 쓰입니다.

3 Node.js LTS — nodejs.org (npm 자동 포함)

→ 뭐하는 프로그램: 자바스크립트(JS)를 컴퓨터에서 돌리는 엔진. 원래 JS는 브라우저 안에서만 도는데, Node.js가 있으면 터미널에서도 JS 코드를 실행할 수 있습니다.
→ Claude Code CLI가 JS로 만들어져서, Node.js 없이는 못 돌아갑니다. 함께 오는 npm은 남이 만든 코드 조각(패키지)을 자동으로 설치·관리해주는 도구.

4 Python — python.org (설치 시 반드시 "Add to PATH" 체크)

→ 뭐하는 프로그램: 또 다른 프로그래밍 언어. 데이터 처리·AI·자동화 스크립트에 많이 씁니다. Node.js와 목적은 비슷하지만 문법·강점이 달라 골라 씁니다.
→ AI API 호출 예제·간단한 자동화가 대부분 Python으로 쓰여 있어, 다른 사람 코드를 실행해보려면 필요합니다.
→ "Add to PATH"란: 컴퓨터가 어디서든 python 명령을 알아듣게 등록하는 옵션. 체크하지 않으면 나중에 "python은 인식할 수 없는 명령"이라는 에러가 납니다.

5 Codex CLI 설치 — PowerShell에서 npm install -g @openai/codex 실행

→ OpenAI GPT 계열을 터미널에서 쓰는 AI 코딩 도구. P-GPT를 통해 사내에서 사용합니다.

npm install -g @openai/codex

현재 이 PC 확인 결과: codex-cli 0.145.0

6 Claude Code 설치 — PowerShell에서 npm install -g @anthropic-ai/claude-code 실행

→ Anthropic Claude를 터미널에서 쓰는 AI 코딩 도구. P-GPT를 통해 사내에서 사용합니다.

npm install -g @anthropic-ai/claude-code

7 설치 확인

PowerShell을 열고 아래 명령을 한 줄씩 입력해서 숫자가 뜨는지 확인합니다.

node --version    → v24.x.x 같은 숫자가 뜨면 OK
npm --version     → 11.x.x
python --version  → 3.14.x
git --version     → 2.55.x
codex --version   → codex-cli 0.x.x
claude --version  → 숫자가 뜨면 OK

숫자가 뜨면 성공이고, "인식할 수 없는 명령"이 뜨면 설치가 안 된 것입니다.

잠깐 — 터미널·PowerShell이 뭔가요?
  • 터미널 (terminal): 마우스 클릭 대신 글자로 컴퓨터에 명령하는 창. 검은 배경에 흰 글씨가 뜨는 화면입니다.
  • PowerShell: Windows 기본 터미널. 여는 방법 — Windows 버튼 누르고 검색창에 powershell 입력 → Windows PowerShell 클릭. 이 문서에서 "PowerShell 열어" = 이 창 하나 열어.
  • 명령어 (command): 터미널에 한 줄씩 치고 엔터 누르면 실행되는 문장. 예: cd(폴더 이동), npm install(패키지 설치).
  • CLI (Command-Line Interface): 위와 같이 명령어로 조작하는 방식. 반대말은 GUI(마우스 클릭). Claude Code CLI = 터미널에서 글자로 쓰는 Claude.

한 줄 요약: 아래 "명령어 순서대로 입력"이라 하면, PowerShell 창을 열고 한 줄씩 붙여넣은 뒤 엔터를 치라는 뜻.

1-2 P-GPT 연결 (⚠️ 가장 많이 헤매는 부분)

사전에 P-GPT API KEY 발급이 필수입니다. IT팀에 요청하세요.

  • 공식 SDK는 ANTHROPIC_API_KEY를 쓰라고 하지만, 사내에서는 반드시 ANTHROPIC_AUTH_TOKEN. 헷갈리면 인증에 실패합니다.
  • 토큰을 코드·채팅·커밋에 붙이지 말 것. 유출 시 IT에 재발급 요청.
  • 버전 번호는 마침표(.)로 씁니다 (예: claude-sonnet-4.6). 하이픈(-)으로 쓰면 오류 납니다.
  • 이 문서 기본값은 ANTHROPIC_MODEL=claude-opus-4.7입니다 — 모든 호출이 Opus로 나가서 Sonnet보다 P-GPT 사용료가 몇 배 더 나올 수 있습니다. 요금이 부담되면 커스텀 모델 옵션으로 등록해 둔 claude-sonnet-4.6으로 /model에서 전환하세요.
  • (claude-opus-4.7은 공식 Anthropic 라인업과 버전 번호가 달라 CLI가 "만료됨"이라고 오해할 수 있습니다. 실제로는 정상 적용된 상태라 무시하고 그냥 쓰면 됩니다.)
  • /model로 대화 중 모델을 바꾸면 현재 세션의 컨텍스트(대화 기록)가 날아갑니다. 모델을 바꾸려면 세션을 종료한 뒤 새로 시작하세요.

Codex CLI — 처음부터 따라하기

요점: Codex는 발급받은 P-GPT API KEY를 OPENAI_API_KEY 환경변수로 읽고, 게이트웨이 주소와 모델은 C:\Users\<사용자>\.codex\config.toml에 적습니다.

  1. P-GPT API KEY를 Codex용 환경변수에 등록
    발급받은 P-GPT API KEY를 넣되, 변수 이름은 OPENAI_API_KEY입니다. 
    $env:OPENAI_API_KEY = "P-GPT API KEY 입력"
[System.Environment]::SetEnvironmentVariable('OPENAI_API_KEY', 'P-GPT API KEY 입력', 'User')
    • 첫 줄은 지금 열린 PowerShell에서 바로 테스트하기 위한 세션용 설정입니다.
    • 둘째 줄은 새 터미널·VS Code·Codex에서 계속 쓰기 위한 사용자 환경변수 등록입니다.
    • 등록 후에는 기존 터미널을 닫고 새 PowerShell을 열어야 반영됩니다.
  2. Codex 설정 폴더와 설정 파일 만들기
    PowerShell에서 아래 명령을 실행하세요. 첫 줄은 폴더를 만들고, 둘째 줄은 VS Code로 설정 파일을 엽니다. 
    New-Item -ItemType Directory -Force "$env:USERPROFILE\.codex"
code "$env:USERPROFILE\.codex\config.toml"
    둘째 줄 실행 후 VS Code 창이 자동으로 열립니다. VS Code 편집 창에 아래 내용을 붙여넣고 Ctrl+S로 저장하세요. projects 경로의 사용자명만 본인 PC에 맞게 바꾸면 됩니다.
    C:\Users\<사용자>\.codex\config.toml
    model = "gpt-5.5"
model_provider = "pgpt"
model_reasoning_effort = "medium"

[model_providers.pgpt]
name = "P-GPT Internal Server"
base_url = "http://aigpt.posco.net/gpgpta01-gpt/v1"
env_key = "OPENAI_API_KEY"

[projects.'c:\users\poscofuturem']
trust_level = "trusted"

[windows]
sandbox = "elevated"
  3. 각 설정이 의미하는 것
    • model = "gpt-5.5" → Codex가 기본으로 호출할 사내 P-GPT 모델명입니다.
    • model_provider = "pgpt" → 공식 OpenAI 기본 서버가 아니라 아래에 정의한 사내 P-GPT provider를 쓰겠다는 뜻입니다.
    • base_url → 사내 P-GPT OpenAI 호환 엔드포인트입니다. Codex는 이 값을 보고 P-GPT로 갑니다.
    • env_key = "OPENAI_API_KEY" → Codex가 토큰을 읽을 환경변수 이름입니다.
    • trust_level = "trusted" → 해당 폴더에서 Codex가 파일을 읽고 수정할 수 있도록 신뢰 저장소로 등록합니다.
    • [windows] sandbox = "elevated" → 현재 이 PC의 Windows Codex 실행 방식입니다.
  4. 새 PowerShell을 열고 키 등록 확인 
    echo $env:OPENAI_API_KEY
    값이 비어 있지 않으면 등록 성공입니다. 단, 토큰 값 자체를 문서·채팅·커밋에 붙이지 마세요.
  5. Codex 실행 
    codex
    대화창이 뜨면 기본 연결은 끝입니다.

Codex에서 자주 헷갈리는 지점:

헷갈리는 것 정답
Claude처럼 ANTHROPIC_AUTH_TOKEN만 넣으면 되나? 아니요. Codex는 현재 설정상 OPENAI_API_KEY를 읽습니다.
OPENAI_API_KEY니까 공식 OpenAI 키인가? 아니요. 이 문서에서는 값으로 사내 P-GPT API KEY를 넣습니다.
OPENAI_BASE_URL 환경변수도 넣어야 하나? 넣지 않습니다. Base URL은 .codex\config.toml의 provider에 적습니다.
공식 모델명을 써도 되나? 아니요. 사내 P-GPT에 등록된 모델명, 현재 PC 기준 gpt-5.5를 씁니다.

최종 확인: codex를 실행한 뒤 간단히 "현재 작업 폴더에 있는 파일 목록을 요약해줘" 같은 요청을 해보세요. 파일을 읽고 응답하면 Codex CLI가 P-GPT 기준으로 정상 동작하는 상태입니다.

Claude Code — 처음부터 따라하기

아래 명령어는 설정값이므로 그대로 복사·붙여넣으세요. KEY 자리만 본인 값으로 바꾸세요.

  1. 위에서 발급받은 P-GPT API KEY를 준비합니다.
  2. Windows 버튼 → 명령 프롬프트 → '+' 클릭 → Windows PowerShell 실행합니다. 실행 후 아래 명령어를 순서대로 입력하세요.
  3. 아래에서 API 키 한 곳만 본인 값으로 바꿔서 전체 복사 후 PowerShell에 붙여넣고 엔터. 기본 모델은 오푸스(claude-opus-4.7)로 채워뒀고, 필요할 때 소넷(claude-sonnet-4.6)으로 바꿔 쓸 수 있도록 커스텀 모델 옵션도 함께 등록됩니다. 
    $env:ANTHROPIC_BASE_URL = "http://aigpt.posco.net/gpgpta01-gpt/"
$env:ANTHROPIC_AUTH_TOKEN = "P-GPT API KEY 입력"
$env:ANTHROPIC_MODEL = "claude-opus-4.7"
$env:ANTHROPIC_DEFAULT_OPUS_MODEL = "claude-opus-4.7"
$env:ANTHROPIC_CUSTOM_MODEL_OPTION = "claude-sonnet-4.6"
    • BASE_URL → 지금 이 터미널 세션에 게이트웨이 주소 세팅. 공식 Anthropic이 아니라 사내 P-GPT로 호출을 돌립니다.
    • AUTH_TOKEN → 지금 이 터미널 세션에 토큰 세팅. 즉시 테스트용.
    • MODEL → 기본으로 호출할 모델. 오푸스(claude-opus-4.7)를 채워뒀습니다.
    • DEFAULT_OPUS_MODEL → "오푸스 기본"을 고를 때 실제로 붙는 버전.
    • CUSTOM_MODEL_OPTION → 커스텀 모델 선택지에 노출할 값. 소넷(claude-sonnet-4.6)을 등록해 필요할 때 전환할 수 있게 합니다.

    다섯 줄 모두 세션 한정입니다 — 새 터미널을 열면 사라집니다. AUTH_TOKEN·BASE_URL만 영구 등록하려면 바로 아래 4번, 모델 값까지 전부 영구 고정하려면 6번 settings.json을 쓰세요.

  4. AUTH_TOKEN·BASE_URL 영구 등록 (다음부터 새 터미널·VS Code 어디서든 자동 인식). API 키 한 곳만 본인 값으로 바꿔서 그대로 복사·붙여넣고 엔터. 
    [System.Environment]::SetEnvironmentVariable('ANTHROPIC_AUTH_TOKEN', 'P-GPT API KEY 입력', 'User')

1-3 GitHub 첫 로그인 (지금은 준비만, 실제 로그인은 나중에)

GitHub는 실제로 처음 git push(내 코드를 GitHub에 올리기)를 할 때 브라우저가 자동으로 열려서 로그인 창을 띄웁니다. GCM(Git Credential Manager)이 이걸 처리해주기 때문입니다. 지금 이 단계에서는 아무것도 안 해도 됩니다 — 다음 조건만 확인하세요:

  • ✅ 사전 조건 2번대로 GitHub 계정(Gmail 가입) 준비됐는지
  • ✅ [1-1]의 Git for Windows 설치 시 GCM이 함께 깔렸는지 (기본값이라 대부분 OK)

실제 첫 로그인 시점: [3-6] "GitHub에 Private 저장소 생성 후 연결"에서 git push -u origin main 명령을 처음 실행할 때, 브라우저가 자동으로 뜹니다. 그때 Gmail로 로그인하면 이후로는 자동입니다.

ℹ️ 참고: PAT(Personal Access Token) 발급은 불필요합니다. 옛날 방식이라 검색하면 자주 나오는데, GCM 덕분에 이 셋업에서는 안 씁니다.

1-4 Git 초기 설정 (한 번만)

전제: 위 사전 조건 2번에 따라 GitHub 계정을 Gmail로 가입해 두었어야 합니다. 아래 user.email에 그 Gmail 주소를 씁니다.

잠깐 — Git이 뭔가요?

명령어 치기 전에 이 정도만 알고 가면 됩니다. 정확한 정의보다 "이해하기 쉬운 비유" 위주로 설명합니다.

  • Git: 내가 쓴 글의 "저장 버튼"을 무한히 누를 수 있는 도구. 매 저장마다 그 시점 상태가 남아서, 언제든 예전으로 되돌릴 수 있습니다. 내 컴퓨터 안에서만 작동.
  • GitHub: Git으로 저장한 것들을 인터넷에 올려두는 창고. 컴퓨터가 고장 나도 여기서 다시 받으면 됩니다. 팀 작업의 공유 공간이기도 함.
  • 저장소 (repository, 줄여서 repo): 프로젝트 하나 = 저장소 하나. 폴더라고 생각하면 됩니다.
  • 커밋 (commit): "지금 상태 저장". 저장할 때 "뭐 바꿨는지" 한 줄 메모(커밋 메시지)를 붙입니다. 예: "로그인 버튼 추가".
  • 브랜치 (branch): 커밋 이력의 갈래. 기본 갈래 이름이 main. 지금은 그냥 "우리는 main에서 작업한다" 정도만 알면 충분.
  • 리모트 (remote): GitHub에 올린 저장소를 가리키는 별명. 관례적으로 origin이라고 부릅니다.
  • push / pull: push = 내 컴퓨터 → GitHub로 올리기. pull = GitHub → 내 컴퓨터로 내려받기.

한 문장 흐름: 파일 수정 → commit으로 저장 → push로 GitHub에 올림 → 다른 곳/사람이 pull로 가져감.

이제 초기 설정

PowerShell 또는 Git Bash에서 아래 5줄. 각각 왜 필요한지:

git config --global user.name "본인이름"
# → 커밋 작성자 이름. GitHub 프로필과 달라도 되지만 팀에서 알아볼 수 있는 이름 권장.

git config --global user.email "GitHub_가입한_Gmail@gmail.com"
# → 커밋 작성자 이메일. GitHub 가입 이메일(Gmail)과 동일해야 커밋에 아바타·프로필이 연결됩니다.

git config --global core.autocrlf true
# → Windows 줄바꿈(CRLF) ↔ Git 저장(LF) 자동 변환. Mac/Linux 팀원과 파일 공유 시 줄바꿈 지옥을 피합니다.

git config --global init.defaultBranch main
# → `git init` 하면 기본 브랜치가 `main`. (구버전 Git은 `master`가 기본이라 팀 컨벤션과 어긋납니다.)

git config --global core.editor "code --wait"
# → 커밋 메시지 편집기를 VS Code로. `--wait`은 VS Code 창을 닫을 때까지 Git이 기다리게 합니다.

credential.helper=manager는 Git for Windows 설치 시 기본값이라 안 건드려도 됩니다. 이게 있어서 PAT 발급 없이도 첫 git push 때 브라우저 OAuth로 GitHub에 로그인됩니다.

1-5 Claude Code 행동 규칙 (선택 사항)

Claude Code에게 "어떻게 코드를 짤지"를 강제하는 규칙 세트. 필수는 아닙니다 — 없어도 CLI는 정상 작동합니다. 코드 품질을 신경 쓰거나 AI가 사변적으로 코드를 부풀리는 게 싫다면 도입하면 됩니다.

(a) Karpathy Guidelines — CLAUDE.md 행동 지침

개념: 플러그인이나 스킬이 아니라, CLAUDE.md 파일에 붙여넣는 텍스트 행동 지침입니다. Claude Code가 대화마다 이 파일을 읽고 규칙으로 따릅니다.

  • 출처: forrestchang/andrej-karpathy-skills (GitHub)
  • 근거: Andrej Karpathy의 트윗 — LLM이 코드 짤 때 저지르는 대표적 실수 목록
  • 핵심 4원칙:
    1. Think Before Coding — 가정 명시, 애매하면 질문. 조용히 추측 금지
    2. Simplicity First — 요청 이상 만들지 않기, 사변적 추상화 금지
    3. Surgical Changes — 요청받은 곳만 건드리기, 인접 코드 "개선" 금지
    4. Goal-Driven Execution — 검증 가능한 성공 기준 정의, 그다음 실행

설치: Claude Code에게 위 GitHub 링크를 주고 "이 CLAUDE.md 내용을 내 C:\Users\<사용자>\.claude\CLAUDE.md에 추가해줘 (기존 내용은 지우지 말고 위에)"라고 요청하면 자동으로 처리합니다.

⚠️ 여기에 추가로 등록해두면 좋은 것 — 컨텍스트 한도: 응답 1회당 약 64K 토큰이 한도입니다. 대용량 작업(긴 파일 전체 리팩토링, 방대한 로그 분석 등) 시 이 한도에 걸릴 수 있으니, CLAUDE.md나 메모리에 이 사실을 등록해두고 작업을 나눠서 진행하는 습관을 들이세요.

메모리란: CLAUDE.md처럼 파일로 관리되는, Claude Code의 장기 기억 저장 공간입니다. 대화 세션이 끝나도 남아 있어서, 반복 참고할 규칙·주의사항을 등록해두면 이후에도 계속 불러와 씁니다.

(b) Ponytail — Claude Code 플러그인

개념: settings.json에 등록해서 쓰는 Claude Code 플러그인입니다. "가장 게으른 = 가장 효율적인" 방식으로 코드를 짜도록 유도합니다 — 라이브러리·표준 기능을 먼저 찾고, 새 코드는 최후에 씁니다.

  • 출처: DietrichGebert/ponytail (GitHub 마켓플레이스)
  • 레벨: lite / full (기본) / ultra — 전환: /ponytail full

설치: Claude Code에게 위 GitHub 링크를 주고 "이 플러그인을 설치해줘"라고 요청하면 settings.json 등록까지 자동으로 처리합니다.

확인:

  • 채팅에서 /ponytail-help 입력 → 명령어 목록 뜨면 성공
  • 상태창(statusline)에 ponytail: full 표시

끄고 싶을 때:

  • Ponytail 일시 종료: 채팅에 stop ponytail / normal mode
  • 완전 제거: settings.json의 enabledPlugins에서 ponytail@ponytail: false

두 개는 함께 써도 되고 하나만 써도 됩니다. Karpathy는 원칙(무엇을), Ponytail은 태도(얼마나 게으르게)를 강제합니다 — 성격이 달라 겹치지 않습니다.

3 Hello Claude — 연결 테스트

P-GPT 환경변수(토큰·Base URL·모델명)가 실제로 CLI/SDK에서 인식되는지 확인. 여기서 성공해야 이후 어떤 프로젝트도 API 호출이 됩니다. Node.js·Python 둘 다 예시 있음 — 본인 스택 하나만 해도 무방.

공통 준비물: [1-2]까지 완료 (환경변수 여러 개 세팅됨).

3-1 Node.js 버전

어디서 하나: 아무 폴더나 새로 만들어서 진행. 예를 들어 C:\Users\POSCOFUTUREM\hello-claude-node.

이 절차가 뭐 하는지:

  • mkdir + cd로 새 폴더 만들고 들어감
  • npm init -y: 이 폴더를 Node.js 프로젝트로 등록. package.json이라는 설정 파일이 자동 생성됨 (프로젝트 이름·버전·설치된 패키지 목록이 들어감).
  • npm install ...: 남이 만든 패키지(여기선 @anthropic-ai/sdk) 다운로드. node_modules/라는 폴더에 실제 파일들이 들어가고, package.json에 이름이 추가됨.

PowerShell 열고:

mkdir hello-claude-node
cd hello-claude-node
npm init -y
npm install @anthropic-ai/sdk

같은 폴더에 hello.js 파일 만들기 (VS Code로 폴더 열기: 터미널에서 code . 입력하면 지금 폴더가 VS Code로 열림 → 좌측 파일 목록에서 우클릭 → New File → hello.js):

hello.js
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic({
  authToken: process.env.ANTHROPIC_AUTH_TOKEN,   // ⚠️ apiKey 아님
  baseURL: process.env.ANTHROPIC_BASE_URL,
});

const msg = await client.messages.create({
  model: "claude-sonnet-4.5",
  max_tokens: 100,
  messages: [{ role: "user", content: "한 문장으로 자기소개해줘." }],
});

console.log(msg.content[0].text);

package.json 수정 한 가지: VS Code에서 package.json 파일 열고 아래처럼 "type": "module" 한 줄 추가:

package.json
{
  "name": "hello-claude-node",
  "type": "module",
  ...
}

→ 위 hello.js에서 import와 최상단 await를 쓰기 위한 스위치. 자세히 알 필요 없고, 위 코드가 돌게 하려면 필요하다 정도만 알면 됩니다.

실행 (PowerShell에서):

node hello.js

3-2 Python 버전

잠깐 — 가상 환경(venv)이 뭔가요?

  • 문제 상황: Python 패키지(anthropic, django, numpy 등)를 그냥 설치하면 컴퓨터 전체에 깔림. 프로젝트 A는 anthropic 0.30, 프로젝트 B는 anthropic 0.40을 써야 한다면? 하나만 살아남고 다른 하나가 부서짐.
  • 해결: 프로젝트마다 격리된 방을 만들어 그 안에만 패키지를 깝니다. 이 "방"이 가상 환경(virtual environment), 줄여서 venv.
  • python -m venv venv: 현재 폴더에 venv/라는 방을 만듬 (첫 venv는 명령, 뒤 venv는 폴더 이름).
  • venv\Scripts\activate: 그 방으로 들어가기. 성공하면 프롬프트 앞에 (venv)가 붙습니다. 이 상태에서 pip install하면 이 방에만 설치됨.
  • 끝나면: deactivate 치면 방에서 나옴. 다음 세션에서 다시 쓰려면 activate 다시.

한 줄 요약: 파이썬 프로젝트마다 이 두 줄(venv 만들기 + activate)로 시작하는 게 관례. 안 하면 나중에 패키지 충돌로 시간을 날리게 됩니다.

어디서 하나: 마찬가지로 아무 폴더. 예: C:\Users\POSCOFUTUREM\hello-claude-py.

4 새 프로젝트 시작할 때 첫날 체크리스트

새 폴더를 만들자마자 이 순서대로 진행합니다. 코드 한 줄 쓰기 전에.
코드부터 짜면 나중에 .env·시크릿·큰 바이너리가 이미 커밋 히스토리에 박혀서 되돌리기 어렵습니다. 방어벽(.gitignore)부터 세우고 시작.

A 잠깐 — .gitignore가 뭔가요?
  • Git은 기본적으로 폴더 안의 모든 파일을 추적하려고 함. 그런데 어떤 파일들은 절대 GitHub에 올라가면 안 됩니다:
    • .env (API 키·비밀번호)
    • node_modules/, venv/ (수천~수만 개 라이브러리 파일. 명령 한 번이면 재설치 가능한데 올리면 저장소가 GB 단위로 부풀음)
    • 자동 생성 캐시 (__pycache__/, *.pyc, .DS_Store)
  • .gitignore 파일은 Git에게 "여기 적힌 이름은 무시해" 라고 지시하는 목록. 파일 이름 자체가 .gitignore (점으로 시작, 확장자 없음).
  • 한 번 커밋된 파일은 히스토리에 영구히 남음. .env를 실수로 커밋한 뒤 지워도 GitHub 클론에는 여전히 존재. 그래서 git init 하기 전에 .gitignore부터 만드는 게 유일한 안전 순서.

한 줄 요약: .gitignore = "이 파일들은 GitHub에 올리지 마" 리스트. 프로젝트 시작할 때 코드보다 먼저.

B 명령어 설명

어디서 하나: PowerShell을 새로 하나 열어서 진행. 예를 들어 홈 폴더(C:\Users\POSCOFUTUREM)에서 새 프로젝트를 만든다고 가정.

여기 나오는 명령어들이 뭐 하는지:

  • mkdir 이름 — "make directory". 지금 있는 폴더 안에 새 폴더 만들기.
  • cd 이름 — "change directory". 그 폴더 안으로 들어가기.
  • && — 앞 명령이 성공하면 뒷 명령도 이어서 실행. mkdir X && cd X = "X 폴더 만들고 그 안으로 이동".
  • git init — 지금 폴더를 Git이 관리하는 저장소로 등록. 이 순간부터 파일 변경 이력이 추적됨.
  • git add 파일명 — 다음 커밋에 포함할 파일 표시.
  • git commit -m "메시지" — 표시된 파일들을 한 시점으로 저장. -m 뒤 따옴표 안이 커밋 메시지.

5 지켜야 할 원칙

5-1 보안 (양보 불가)

  • API 키·토큰은 절대 코드에 직접 쓰지 않는다 → os.getenv() / process.env
    → 코드는 Git에 올라가고 팀 전체가 봅니다. 키가 박히면 push 순간 유출.
  • .gitignore에 .env 넣는 게 코드 첫 줄보다 먼저
    → 한 번 커밋된 파일은 히스토리에서 완전 삭제가 어려움. 처음부터 안 올리는 게 유일한 방어.
  • 실수로 커밋한 키는 삭제로 안 사라짐 → 즉시 IT에 재발급 요청
    → Git 히스토리·클론된 로컬·GitHub 캐시에 다 남아있음. 삭제해도 이미 노출된 값은 회수 불가.
  • 슬랙·카톡·메일로 토큰 전송 금지 → 비밀번호 관리 도구 사용
    → 메신저 로그·백업·서버에 평문으로 남아 유출 경로가 늘어남.

5-2 Git (양보 불가)

  • 프로젝트 첫날 git init. "완성되면 올릴게"는 실패 공식
    → 완성 전에 반드시 뭔가 부수게 되고, 이력이 없으면 되돌릴 앵커가 없음.
  • 커밋은 자주, 작게. 하루치 몰아 커밋 금지
    → 문제 생겼을 때 어느 커밋이 원인인지 좁혀 찾을 수 있음(Git엔 이걸 도와주는 git bisect 기능이 있음). 큰 커밋 하나에 여러 변경이 섞여 있으면 되돌리기도 큼.
  • 커밋 메시지는 feat: / fix: / docs: / refactor: / chore: 접두어
    → 나중에 히스토리 볼 때 종류별로 훑기 쉬움. 이 접두어 규칙을 "Conventional Commits"라고 부르는데, 오픈소스에서 널리 쓰는 관례.
  • 큰 리팩토링 전 git commit -m "checkpoint" 필수
    → 리팩토링이 망하면 여기로 되돌릴 수 있어야 함.
  • 회사 프로젝트 저장소는 Private
    → 사내 URL·API 구조·내부 로직 노출 방지.

5-3 코드 작성

  • 작동하는 코드 먼저, 예쁜 코드 나중 (Make it work → right → fast)
    → 최적화·리팩토링은 정상 동작이 확정된 뒤에 해야 안전. 순서 뒤집으면 뭘 부쉈는지 모름.
  • 한 번에 한 곳만 수정 → 실행 → 확인 → 커밋
    → 여러 곳 동시에 바꾸면 문제 생겼을 때 원인 특정 불가.
  • AI가 준 코드는 실행 전에 반드시 읽고 이해
    → AI는 존재하지 않는 API·라이브러리 함수를 자신있게 만들어냄. 검증 없이 붙이면 원인 모를 에러.
  • 매직 넘버·매직 스트링 금지 → 상수로 뽑기
    → 86400이 뭔지 3개월 뒤엔 모름. SECONDS_PER_DAY라고 이름 붙이면 됨.
  • 함수 하나는 한 가지 일만
    → 여러 일 섞이면 재사용·테스트·수정 다 어려움. 단일 책임 원칙.

5-4 에러 대응

  • 에러 메시지는 마지막 줄부터 읽는다
    → 스택 트레이스 마지막 줄이 실제 원인. 위로 갈수록 호출 경로.
  • 순서: 메시지 정독 → 구글 검색 → AI에 질문 → 사람에 질문
    → 앞 단계에서 풀리는 문제로 사람 시간을 뺏지 말 것. 사회적 비용 있음.
  • 30분 룰: 한 문제에 30분 이상 매달리지 말 것
    → 30분 넘게 막히면 접근이 틀렸을 가능성 큼. 관점 전환·조언이 더 빠름.
  • print() / console.log()는 프로도 씀. 부끄러워하지 말 것
    → 디버거보다 빠를 때 많고, 원인 특정에 가장 확실.

5-5 AI 협업

  • AI는 자신있게 틀린 코드를 준다. 검증 필수
    → 확률적 생성이라 존재하지 않는 API·문법도 그럴듯하게 만듦. 컴파일·실행이 유일한 검증.
  • 요청할 때 맥락 함께 전달: 언어, 입력, 출력, 제약
    → 맥락 없이 물으면 일반론적 답이 오고, 프로젝트에 안 맞음.
  • 아키텍처 결정은 AI에게 위임하지 말 것 (판단은 사람이)
    → AI는 트레이드오프 무게를 실측 없이 답함. 사람이 우선순위를 정해야 함.
  • 대화 길어지면 결정사항 별도 문서화 (DECISIONS.md)
    → AI 대화창은 세션이 끝나면 사라짐. 결정만 뽑아 남겨두면 다음 대화에서 재현 가능.

5-6 비용 관리 (사내 API 필수)

  • 개발 중 max_tokens는 작게 (100~500)
    → 개발 중엔 결과 형식만 확인하면 됨. 토큰은 곧 돈.
  • 같은 입력에 같은 출력 → 캐싱 검토
    → 결정론적 결과를 매번 호출하면 사용료 낭비.
  • 호출 로그 남기기 (월말 추적용)
    → 청구서만 보면 어느 코드가 원인인지 모름. 로그가 있어야 절감 대상 특정 가능.
  • P-GPT 사용량은 회사 계정에 청구됨 — 무한 루프 조심
    → while(True): claude.call() 한 줄로 하루에 수십만원 나갈 수 있음.

5-7 시간·정신 관리

  • 하루 8시간 코딩 < 하루 1~2시간 꾸준히
    → 코딩은 집중력 게임. 지친 8시간이 만든 코드는 다음 날 다시 씀.
  • 안 풀리면 잠깐 잘 것. 진지하게 하는 말 — 자고 나면 풀리는 경우가 많음
    → 뇌가 무의식적으로 문제를 정리함. 유명한 현상, 미신 아님.
  • 완벽주의 = 프로젝트의 적. 80% 이해하고 다음으로
    → 100%를 노리면 첫 단계에서 멈춤. 80%에서 다음 단계로 가면 나중에 자연히 100% 됨.

5-8 문서화

  • README.md는 첫날부터, 계속 업데이트
    → "나중에 쓸게"의 나중은 없음. 매일 조금씩이 유일한 방법.
  • 주석은 "왜"를 쓴다 (뭘 하는지는 코드가 말해줌)
    → 코드는 "무엇"을 이미 표현. 주석은 "왜 이 선택"이라는 못 남는 정보를 붙잡음.
  • 큰 결정은 DECISIONS.md에 한 줄씩 로그
    → 3개월 뒤 "이거 왜 이렇게 했지?"를 스스로에게 물음. 미리 답을 남기는 것.
  • 3개월 뒤 자신은 지금 자신을 기억 못 함
    → 인간의 기본값. 미래의 나를 남으로 취급하고 문서 남기는 게 맞음.

변수명 용도
