# P-GPT Claude 경로 — 생각(thinking) 설정이 전달되지 않고 생각 구간이 스트림에서 비어 긴 요청이 시간 초과로 끝납니다

작성 2026-09-09 · 2026-09-14 추가 실측 반영 · 대상 P-GPT(`aigpt.posco.net/gpgpta01-gpt`) 운영팀 · 측정 주체 사내 사용자(Claude 연동 앱 · Claude Code)

## 요약

P-GPT 의 Claude 경로에서 두 가지가 관측됩니다. 첫째, 요청에 실은 생각 관련 설정(`thinking`,
`output_config.effort`)이 모델에 전달되지 않습니다. 둘째, 모델이 생각하는 동안의 스트림 이벤트
(`thinking` 블록)가 클라이언트에 오지 않습니다. 그 결과 생각이 기본으로 켜진 모델(`claude-opus-5`)은
긴 요청에서 첫 글자가 오기 전에 180초 동안 유효한 내용 이벤트가 없다가 스트림이 닫힙니다. 9월 14일
추가 실측에서는 **텍스트가 계속 오던 스트림도 요청 시작 약 180초에 닫혔습니다.** 따라서 단순 idle
timeout보다는 Claude 스트림 전체에 적용된 **절대 수명 상한(absolute request/stream timeout)** 가능성이
더 큽니다. 클라이언트가 비스트리밍으로 재시도하면 300초 뒤 504 가 되어, 종전 폴백은 한 요청에
8분을 소모하고도 실패했습니다.

## 관측 사실

같은 질문(짧은 셈 문제 · 답 두 줄)을 모델과 설정만 바꿔 보내고, 응답의 `usage.output_tokens` 에서
글자 수에 해당하는 몫을 뺀 **초과 토큰**으로 생각량을 읽었습니다. 판마다 두 번씩 보냈습니다.

| 모델 | 설정 | 초과 토큰 | 생각 블록 이벤트 |
|---|---|---|---|
| claude-opus-4.7 | 없음 | 15 | 0 |
| claude-opus-4.7 | `thinking: {type: adaptive}` | 15 | 0 |
| claude-opus-4.7 | `thinking: {type: enabled, budget_tokens: 4096}` | 16 | 0 |
| claude-opus-5 | 없음 | 91 | 0 |
| claude-opus-5 | `thinking: {type: adaptive}` | 90 | 0 |
| claude-opus-5 | `output_config.effort` low / high / xhigh / max | 198 / 177 / 199 / 182 | 0 |
| claude-opus-5 | `thinking: {type: disabled}` | 192 | 0 |

읽히는 것은 셋입니다.

1. **설정이 모델에 닿지 않습니다.** 4.7 은 `thinking` 을 어떻게 실어도 생각을 안 하고, Opus 5 는
   `disabled` 를 실어도 생각을 합니다. `effort` 넷의 생각량이 같습니다. 참고로
   `enabled + budget_tokens` 는 Anthropic 문서상 4.7 에서 400 이 나야 하는 형식인데 200 으로 옵니다.
2. **생각은 모델 기본값이 정합니다.** Opus 5 는 문서상 생각이 기본으로 켜진 모델이라 설정과 무관하게
   생각하고, 그 토큰이 `output_tokens` 에 계산됩니다(위 표의 초과분).
3. **생각 구간이 스트림에서 비어 있습니다.** Opus 5 가 생각한 판에도 `content_block_start(type:
   thinking)` · `thinking_delta` 이벤트가 0 입니다. 같은 요청을 Anthropic 공식 API(`api.anthropic.com`)
   로 보내면 첫 글자 전에 생각 이벤트가 오고, 그 생각량(99)이 초과 토큰(97)과 일치합니다.

실제 실패 세 건의 시간표입니다(Claude 연동 앱의 요청 기록 · 모델 claude-opus-5 · 긴 문서 생성 요청).

| 요청 시작 | 종료 | 소요 | 종료 사유 |
|---|---|---|---|
| 09-07 14:07:02 | 14:15:02 | 480초 | 스트림 180초 무응답 후 닫힘 → 비스트리밍 재시도 → HAProxy 504 |
| 09-09 18:53:25 | 19:01:26 | 481초 | 같음 |
| 09-09 19:03:31 | 19:11:31 | 480초 | 같음 |

480초 = 스트림 상한 180초 + 비스트리밍 앞단 상한 300초입니다. 스트림 쪽 첫 이벤트(`message_start`)는
0.3초에 옵니다. 실패에 따라 그 뒤 아무 이벤트가 없기도 하고, 텍스트 조각이 오다가 180초에 잘리기도
합니다. `message_start` 의 `usage.output_tokens` 가 0 으로 오는 것도 함께 적어 둡니다(공식 API 는 1).

같은 게이트웨이를 쓰는 Claude Code(VS Code 확장 · 모델 claude-opus-4.7)에서도 `message_start` 뒤
180초 무응답 후 닫히는 판이 8-27, 9-9 두 차례 기록됐습니다. 4.7 은 이 경로에서 생각을 안 하므로 이
침묵은 생각이 아닙니다. 원인은 저희 쪽에서 가릴 수 없어 별도 항목으로 둡니다.

## 2026-09-14 추가 실측 — 입력 크기와 180초 절단

Atelier의 동일한 Opus 5 plan 조건에서 원문을 25%부터 100%까지 바꾸어 확인했습니다. 원문 전체는
약 38.9KB이고, 종전 전체 요청의 첫 봉투는 약 48,807자·30,350 입력 토큰이었습니다. 25% 입력에서도
요청이 즉시 거절되지는 않았고, 모델 출력이 시작된 뒤 180초 경계에서 잘렸습니다. 따라서 현재까지
**입력 크기 제한에 즉시 걸린다는 증거는 없습니다.** 입력 크기가 Opus 5의 첫 출력 시간을 늘려
180초 경계를 넘기게 하는 촉발 요인일 수는 있습니다.

대표 실측은 다음과 같습니다.

| 조건 | 관측 결과 |
|---|---|
| 25% plan | 출력 1,094자까지 도착한 뒤 요청 시작 약 180초에 스트림 종료 |
| 100% plan · 출력 상한 24K | 1·2차 각 180초 동안 본문 0자, 3차에서 12,472자 수신 후 절단, 4차에서 완료 · 총 약 9분 29초 |
| 100% plan · 출력 상한 16K | 첫 바퀴에서 990자 수신 후 약 180초에 절단, 새 Messages 요청으로 이어쓰기 진입 |
| render · 출력 상한 64K | 첫 바퀴에서 HTML 1,481자 수신 중 180초 절단, 다음 요청도 180초 동안 본문 0자 |
| 비스트리밍 | 완성 응답을 기다리다가 약 300초에 HAProxy `504 Gateway Time-out` |

특히 plan과 render에서 **본문 조각이 실제로 계속 전달된 경우에도 시작 후 약 180초에 종료**되었습니다.
이는 클라이언트가 ping을 보내지 않아 발생한 단순 유휴 시간 초과만으로 설명되지 않습니다. heartbeat가
도움이 되는지는 별도 확인이 필요하지만, 절대 수명 상한이라면 heartbeat만으로는 해결되지 않습니다.

스트림 종료 형태도 기록해 둡니다.

- HTTP/SSE 연결과 `message_start`는 약 0.3초 안에 열립니다. 게이트웨이가 완전히 무응답인 것은 아닙니다.
- 본문이 없던 판은 `message_start` 뒤 약 180초에 종료 신호 없이 EOF가 옵니다.
- 본문이 있던 판도 같은 약 180초 경계에서 `message_stop` 없이 EOF가 옵니다.
- Atelier 밖에서는 그동안 업스트림이 실제로 무응답인지, thinking 이벤트를 게이트웨이가 누락·버퍼링하는지
  구분할 수 없습니다.
- 비스트리밍 504의 짧은 HTML 본문은 모델 답변이 아니라 HAProxy가 생성한 오류 문서입니다.

## 클라이언트 이어쓰기의 한계

Anthropic Messages/SSE 응답에는 끊어진 생성을 다시 붙잡을 cursor, event ID 또는 resume token이
없습니다. `Last-Event-ID`로 재접속할 수 있는 이벤트 ID도 관측되지 않았습니다. 따라서 클라이언트가
기존 스트림에 재접속하는 **전송 계층의 진짜 resume**는 할 수 없습니다.

Atelier에서는 비스트리밍 폴백을 제거하고 다음의 의미적 이어쓰기를 시험했습니다.

1. 받은 본문 조각을 보존합니다.
2. 같은 원문·시스템 접두사 뒤에 받은 조각을 assistant 메시지로 싣습니다.
3. 그 뒤부터 계속 쓰라는 user 메시지를 붙여 새 SSE 요청을 보냅니다.

원문과 시스템 접두사의 prompt cache 경계는 유지됩니다. 완료된 실측 한 판에서는 일반 입력 293토큰,
cache read 33,090토큰, cache write 13,559토큰이 기록되어 캐시 재사용 자체는 확인했습니다. 그러나 이는
중단된 모델 실행 상태를 잇는 것이 아니므로, 새 요청마다 Opus 5가 문맥을 다시 읽고 생각합니다. 그 결과
출력이 멈춘 뒤 다시 수 분간 생각할 수 있고, 새 추론·출력·캐시 write 비용이 추가됩니다. 또한 180초에
잘린 바퀴는 최종 usage 이벤트가 오지 않아 클라이언트 기록이 0이어도 업스트림 과금 여부를 확인할 수
없습니다. 이 방식은 산출물을 잃지 않기 위한 완화책이지 게이트웨이 수정의 대체재가 아닙니다.

## 여쭙는 것

1. **Claude 경로가 Bedrock 의 어느 API 로 연결되어 있는지** — Messages API 호환 엔드포인트
   (`/anthropic/v1/messages` · SSE)인지, `InvokeModel`/`Converse`(AWS 이벤트 스트림)인지. 후자라면
   요청·응답을 변환하는 층이 있고, 위 관측(설정 누락 · 생각 이벤트 누락 · `output_tokens` 0)은 그 변환이
   `thinking`/`output_config` 필드와 `reasoningContent` 이벤트를 옮기지 않는 모양과 일치합니다.
2. **`thinking` · `output_config` 를 요청 그대로 전달하고, 응답의 생각 블록 이벤트를 클라이언트로
   되돌려 줄 수 있는지.** 설정이 전달되면 생각 길이를 줄여 180초 안에 완료될 가능성이 커지고,
   생각 이벤트가 전달되면 사용자에게 실제 진행 상태를 표시할 수 있습니다. 다만 출력 중에도 180초에
   잘린 추가 실측 때문에 thinking 이벤트 전달만으로 절대 수명 상한이 해결되지는 않습니다.
3. **스트림 시작 후 약 180초의 절대 수명 상한을 장기 생성 요청에 한해 늘리거나 해제할 수 있는지**
   확인 부탁드립니다. 어느 층인지는 저희 쪽 실측(2026-09-17)으로 좁혀졌습니다 — 절단의 마지막
   바이트에 `{"type":"error","error":{"type":"api_error","message":"내부 서버 오류: HTTP request
   execution did not complete before the specified timeout configuration: 180000 millis"}}` 가
   실려 오므로 P-GPT 앱 쪽 요청 실행 시한으로 보입니다. **같은 요청을 `stream:false` 로 보내면
   180초를 넘겨 살아 있고**(119초 `200` 실측) 300초에 앞단 HAProxy 가 HTML `504` 를 냅니다 —
   즉 이 시한은 **스트림 경로에만** 걸려 있는 것으로 보입니다. 경로에 따라 값이 다른 까닭과,
   스트림 경로의 값을 조정할 수 있는지 알려 주시면 감사합니다. 단순 idle timeout 이 아닌 것은
   확인했습니다(텍스트 26,836바이트가 끊김 없이 흐르던 판도 같은 자리에서 잘렸습니다).
   ⚠ 아울러 앞단 HAProxy 의 `timeout server` 300초도 **자동 대화 압축처럼 원래 오래 걸리는
   요청**을 잘라, 같은 작업이 여러 번 재시도되며 총 17분을 소모하고도 결과를 못 내는 판이
   기록됐습니다(2026-09-14). 두 값을 함께 검토해 주시면 좋겠습니다.
4. 게이트웨이가 180초 뒤 클라이언트 연결을 닫을 때 **Bedrock/Anthropic 업스트림 생성도 취소하는지**,
   아니면 백그라운드에서 계속 생성·과금되는지 확인 부탁드립니다. 후자라면 클라이언트에는 usage가
   오지 않으면서 비용만 발생할 수 있습니다.
5. (부수) 4.7 에서 `message_start` 뒤 무응답으로
   닫힌 판(9-9 15:57~15:59 · 클라이언트 Claude Code 2.1.266)의 서버 쪽 기록을 확인해 주실 수 있는지.

## 재현 방법

인증 헤더만 바꾸면 그대로 돕니다. 두 요청의 `usage.output_tokens` 를 견주면 1·2 가 보이고, 스트림에서
`thinking` 이벤트가 없는 것으로 3 이 보입니다.

```bash
# Opus 5 · 설정 없음 — 생각이 기본으로 켜져 output_tokens 가 글자 수보다 훨씬 큽니다
curl -sN http://aigpt.posco.net/gpgpta01-gpt/v1/messages \
  -H 'content-type: application/json' -H 'anthropic-version: 2023-06-01' -H 'x-api-key: <키>' \
  -d '{"model":"claude-opus-5","max_tokens":1024,"stream":true,
       "messages":[{"role":"user","content":"1부터 100까지의 정수 가운데 3 또는 5의 배수의 합, 그리고 그 수들 가운데 7의 배수인 것의 개수. 풀이 없이 답만 두 줄로."}]}'

# Opus 5 · thinking disabled — 공식 API 에서는 생각이 꺼져야 하는데 위와 같은 output_tokens 가 옵니다
curl -sN http://aigpt.posco.net/gpgpta01-gpt/v1/messages \
  -H 'content-type: application/json' -H 'anthropic-version: 2023-06-01' -H 'x-api-key: <키>' \
  -d '{"model":"claude-opus-5","max_tokens":1024,"stream":true,
       "thinking":{"type":"disabled"},"output_config":{"effort":"high"},
       "messages":[{"role":"user","content":"1부터 100까지의 정수 가운데 3 또는 5의 배수의 합, 그리고 그 수들 가운데 7의 배수인 것의 개수. 풀이 없이 답만 두 줄로."}]}'
```

## 저희 쪽에서 한 것

종전의 비스트리밍 재호출은 제거했습니다. 현재 앱은 긴 산출물에서 180초 절단을 감지하면 받은 조각을
보존하고 새 SSE 요청으로 의미적 이어쓰기를 하며, 이미 본문이나 도구 조각이 나온 요청 전체를 처음부터
재실행하지 않습니다. Opus 5의 첫 출력 지연을 줄이기 위해 plan 출력 상한은 16K, render와 patch는
32K로 제한했습니다. 이는 실패율과 손실을 낮추기 위한 임시 완화이며, 위에서 설명한 재추론 시간과 비용은
남습니다. 측정에 쓴 스크립트와 원본 응답은 보관하고 있어 필요하시면 드립니다.
