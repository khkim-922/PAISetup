# 출처 — 회의실 예약 스킬

밖의 표준을 빌리지 않았다 — 회의실 예약 앱은 사내 앱이라 공개 스킬 · 명세가 없다. 앱의 자리와 꼴은 앱이 내려 주는 화면 코드(로그인 없이
받는 자바스크립트 묶음)에서 읽고, 회사 PC 에서 실물로 쟀다.

## 회사 PC 에서 잰 것 (2026-11-10)

- 사내 세션(ep-login 의 세션 파일)만으로 SSO 넘김 → 출입증 → 읽기 · 넣기 · 고치기 · 지우기가 다 돈다. 출입증 바꾸기가 한 번 지고
  곧 다시 선 일이 있다 — 손이 한 번 더 받아 본다
- 넣으면 M365 일정 이벤트와 회의실 정책이 켠 Teams 링크가 저절로 생긴다. 참석자에게 가는 회의 안내는 회사 메일로 조금 늦게 온다(쓰는 사람의 말)
- 앱의 미리 검사는 정책(타사 · 승인 · 시간 제한)만 본다 — 겹치는 예약 · 지난 시각은 통과하고, 지난 시각 예약은 넣어진다
- 메일 주소록(company-mail `people`)과 앱의 사람 목록은 같은 사람을 같은 메일 주소로 든다. 앱 목록에는 직책이 없고 동명이인이 많다

## 회사에서 아직 안 잰 것

- 승인이 필요한 회의실에 넣은 예약의 답 꼴(`pending_approval` 로 읽는다)
- 고치기에서 회의실을 바꾸는 판 · 참석자를 바꾼 판에 가는 안내
- 반복 예약을 가르는 칸 — 내 예약에 반복이 없어 실물 꼴을 못 봤다. `is_series` 는 화면이 반복을 싣는 두 칸(`is_recurring` · `recurring_end_date`)으로 가린다
- 넣기 · 고치기의 `status` 를 앱이 그대로 믿는가 — 화면처럼 `confirmed` 를 보내고, 승인 회의실은 앱이 `pending_approval` 로 바꾸는지 다시 읽어 본다
- 넣기 답이 감싼 꼴로 오는 일 — 잰 답은 예약 그대로(`id` 가 맨 위)였다
